# The event log

What ccsaver records on your machine, what it never records, and what `saved` adds up from it. Off by default, and no code in ccsaver sends it anywhere.

`ccsaver log on` creates `~/.config/ccsaver/log/` (700), and from then on the hook and the command append one JSON line per event to `events-YYYY-MM.jsonl` (600). The month, in UTC, is the only rotation, and nothing is ever deleted for you. The folder is the switch: without it nothing is recorded and no file is created. `ccsaver log off` renames the folder to `log.off/` with its data, `ccsaver log on` brings it back, and `rm -rf ~/.config/ccsaver/log ~/.config/ccsaver/log.off` deletes it. Either one typed while the log is already so answers `the log is already on` or `off` and touches nothing, the folder included.

It holds metadata only, and it never leaves your machine:

- `gate`: every `Read` the hook sees in a plugged project, allowed or denied. The path relative to the plugged root (a file outside it is `"inside": false`, with no path), `offset` and `limit`, or the `pages` of a PDF, lines (`null` when the file was past the byte limit and its lines were never counted), bytes, the limits and the adapter in force, the model the session was running and the context its last request carried (`model` and `context`, the count being `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` of the same transcript line; both `null` when Claude Code hands the hook no transcript, when the transcript holds neither, or when the `Read` comes from a subagent, because the transcript the hook is handed is the session's and speaks for the session, not for the subagent), the decision (`allow`, `deny`, or `rewrite` when an adapter with `rewrite` turned the denial into a read of the first `maxLines` lines, the `offset` and `limit` then being the ones the hook wrote in the model's place) and its reason (`under`, `lines`, `tokens`, `range`, `binary`, `unreadable`, `malformed`, `outside` for a whole-file read of a file outside the root, which is never denied, and `untakeable` for one over the limits that `bulk-read` would refuse to send, by its name or place, by a private key or an access token in its text, or as a binary its first 8 KB did not reveal, which is never denied either, the hook reading a file it is about to deny once for that, up to 1 MB), the milliseconds since the hook's process started, and the ids Claude Code hands the hook (`session_id`, `tool_use_id`, `agent_id`, `agent_type`, `permission_mode`), which are the ones in the session transcript. A path that is no regular file, a folder or a pipe, is `unreadable` without being opened, so a pipe with no writer at its other end cannot hold the hook.
- `delegate`: one per `bulk-read` or `code-write`. Mode, number of files and how many sat outside the root, characters sent, who answered, why the external worker did not (`outside`, `no worker`, `no key`, `key moved`, `key unreadable`, `key malformed`, `not https`, `status`, `incomplete`, `length`, `timeout`, `not json`, `redirect`, `unreachable`), HTTP status, milliseconds, characters of the answer, whether a `bulk-read` answer stopped at its output limit and was kept (`cut`), the input tokens the external endpoint reported in its `usage` block (`inTokens`, absent when it reported none), the citation tally, the cost of the fallback, the exit code and, for `code-write`, whether there was a target, what the formatter did, the lines written and how many names tripped the `warn:` line.
- `handoff`: `warned`, once per warning, with the token count (`context`), the `limit`, which multiple of it (`tier`) and the `model`; and `written`, with the `lines` and `bytes` of a handoff `ccsaver handoff write` kept and whether it `replaced` an earlier one of the session, never its text.
- `note` and `fail`: the one-line messages the command prints on stderr, a refusal in an unplugged project included; the note about a failing formatter is recorded without what the formatter printed, because that can quote the generated code. A mistake on the command line (an unknown command, a command given the wrong arguments, an unknown option, a folder that is not there, a `worker.json` that is malformed or cannot be read, a state folder that cannot be made private) is a `fail`, never a `crash`: `crash` is for a bug in ccsaver, so a machine the user can fix never lands there. `config`: `plug`, `unplug`, `worker set` (host and model), `worker claude` (pinned or not, never the path), `fallback`, `log`, `handoff` (on or off, or the limit), `price` (which model or the worker, and the figure), `launcher` (where it went), `adapter limits` (the adapter and the limits `ccsaver adapter` wrote), and the bare fact of a `key set`; each one only when the value changed, so a setting typed again with the value it already has, which the command answers with `already`, leaves no line. `doctor`: how many `ok`, `warn` and `FAIL` lines, and, one per plugged project, the probe `doctor` sent through the hook, a line with the fields of a `gate` one and `"tool_use_id": "doctor"`; before 0.27 the probe was a `gate` line so marked, which `saved` and `doctor` still leave out of a month written then. `crash`: name, message and first stack lines of an exception, the ones the hook swallows to let the read through included, and the adapter it could not load (`"where": "hook adapter"`), which is why the `gate` line beside it carries the default limits under the adapter’s name.

To learn the model and the context, the hook reads the tail of the session transcript Claude Code names in `transcript_path`, **the last 16 KB first and the last 256 KB only when no assistant line sits in them**, and takes the `model` and the `usage` of the last assistant line (64 KB alone left a quarter of the lines without one, because a single tool result can be longer than that, and 16 KB alone would leave more; the line the hook wants is the one that asked for the tool, which is almost always in the last few KB, so the [short read answers first](development.md#reading-the-model-out-of-the-transcript)) — parsed as JSON, so a model name written in the conversation is not mistaken for the one in force. Nothing else is read from the transcript and nothing from it is recorded but that name and that count. It costs nothing while the log is off, because the hook only looks when it is about to write a line. The handoff hook reads the same tail of the same file at the end of every turn, for the token count beside that name, and its `warned` line records those two and nothing else.

Never recorded: the contents of a file, the worker's answer, the text of `--question` or `--spec`, the key, request headers, anything from the transcript but the model name and the token count. A stored key that turns up inside any line, from any command, is written as `[key]`, and so is one that turns up in what a command prints, the worker's answer included; that holds for keys of 8 characters or more, because replacing anything shorter would eat unrelated text. In an unplugged project the hook records nothing, because it exits before starting Node; and while the log is off, in a plugged project with no adapter, `hooks/gate` answers a ranged `Read` or a file under the limits in `sh` too, before Node starts, [4 ms instead of 24](development.md#hook-overhead-per-read), and hands Node the rest through a pipe: the log on, or an adapter, sends every `Read` to Node, because a line of the log and a limit of the adapter's are Node's to read. A failure to write the log never changes a decision of the hook, an exit code or an output. A failure to *read* it does: a month's file that is there but cannot be read stops `ccsaver saved` with the name of the file, instead of counting as a month with no events, and `doctor` turns it into one `FAIL log:` line and reports everything else as usual.

Every line carries `v` (the format version), `ts`, `kind`, `session` (`CLAUDE_CODE_SESSION_ID`, or `null` outside Claude Code, cut at 200 characters), `pid` and `by`, the version of ccsaver that wrote it, because the rules behind a field change between versions and a month's file outlives an update; a line that would pass 4,000 bytes is replaced by a stub with its size, so one runaway message cannot bloat the log. The session id is cut because it is the one field of that stub which comes from outside, and a long one would have carried the stub past the cap it exists to enforce. Processes that write at once do not tear each other's lines: 8 of them appending together left 0 broken lines of 8,000 at 4,000 bytes a line, and 0 of 320 at 1 MB a line (Linux, ext4). While the log is on, the hook also measures the file behind a ranged `Read`, which it otherwise skips. `doctor` leaves one `doctor` event per plugged project, the probe it sends through the hook on a throwaway file it writes inside the root for a moment, so the `gate` lines hold the session's reads and none of `doctor`'s.

What the log cannot say: whether a line came from work or from developing ccsaver, which only `root` hints at; what the model did after a denial beyond a ranged `Read` of the same file in the same session, which [`saved`](#saved) counts from these lines, a `cat`, a `Grep` or a delegation being in the session transcript only; which check a `doctor` line failed, since it keeps the counts only; the settings made before `log on`; a read made with `cat`, `head` or `sed` through Bash, which in Claude Code's `auto` permission mode is how the harness tells the model to read, so a whole file can enter the context and leave no `gate` line; and a call killed before it ended, which leaves no `delegate` line, or one that ran while the log was being switched off, whose lines went nowhere.

## saved

`ccsaver saved` adds up [the event log](#the-event-log) and says what the month cost against what it would have cost without the plugin. `/ccsaver:saved` runs it from a session and reads the answer back with every caveat the foot of the report carries, the part a summary drops first. It is the long form of doctor's `spent:` line, reads the log only, never calls a worker and writes nothing but the price you set.

```
ccsaver saved            # the month in course
ccsaver saved 2026-08    # that month
ccsaver saved all        # every month the log still holds, one line in memory at a time
```

It needs prices, in dollars per million input tokens, because ccsaver cannot see what your session pays. **A price belongs to a model, not to the month**, because the model changes and the rates are far apart:

```bash
ccsaver price claude-opus-5 5.00      # what your session model charges
ccsaver price claude-fable-5-1 10.00  # and any other you work on
ccsaver price worker 0.10             # the cheap worker, or 0 when its tier is free
ccsaver price                         # what is set, one to a line
```

The hook records which model was running for every read it sees ([the event log](#the-event-log)), by the id the transcript writes, `claude-opus-5` or a Bedrock or Vertex one such as `us.anthropic.claude-sonnet-4-5-20250929-v1:0`, so the report prices each model's reads at that model's own rate, never one number over a month that changed model. A model that turns up in the log with no price of its own is **named, with the command that gives it one, and its tokens are left out of the sum** — a rate borrowed from another model would be a number without a source. Reads the hook could not name a model for are counted apart in the same way. When that leaves no denied read with a price at all, the report draws no bars and says there is no `without` side to draw: an empty column set against a full one reads as a loss, and a missing rate is not a loss.

They live in `~/.config/ccsaver/prices.json` (600), apart from `worker.json` so that the file holding the `fallback` switch gains no surface. A model price must be above zero, and the worker's may be `0`, which is the free tier of a provider said out loud: the report then writes *the worker is free* instead of asking for a number that does not exist. Wherever the worker is named, the list, the price confirmation, the foot of the report, the model from `worker.json` rides in brackets beside it, so `worker` alone never stands in for an endpoint you pointed elsewhere months ago. No price is shipped: one would go stale, and a number without a source is what this project refuses to print. With no model priced the report counts tokens and stops there. A `prices.json` that is there but malformed or unreadable stops the command, as `worker.json` does, and so does a month's log file that cannot be read: a report that counted it as an empty month would be the one lie this command cannot afford. A `prices.json` carrying the single `main` price of 0.13 and earlier is refused rather than read as the rate for every model.

Adding a month up never holds it in memory: the reader hands the tally [one row at a time](development.md#adding-up-a-month-of-the-log), so `all` over a year costs what the longest month costs to read, not what the year weighs.

**The numbers are a band, never a point.** A real `Read` measured [1.9–2.8× the bytes/4 estimate](measurements.md#the-hooks-token-estimate-vs-a-real-read), so both columns carry that multiplier. It is the same unknown on both sides, so the two arms pair low with low: the dollars swing by half, and the percentage barely moves. Read the percentage.

```
ccsaver saved · 2026-09

  denied     181 whole-file reads, 1.83 M tokens by bytes/4
  instead    63 ranged reads while plugged, 0.08 M tokens
  delegated  112 calls · 98 external (1.13 M tokens) · 14 paid Haiku ($0.2019)

  without    $10.45 - $15.40    ██████████████████████
  with       $0.76 - $0.97      █·····················
  saved      $9.69 - $14.43     93 % - 94 %

  at $5/M for claude-opus-5 and $0.1/M for the worker (gemini-flash-lite-latest)
```

`instead` is the line that keeps the rest honest: a denial is not a saving, because the model then reads the file by ranges and pays for those. It counts every ranged read in a plugged project, not only the ones a denial caused, which errs towards charging ccsaver for reads it never provoked, and a read the hook rewrote into the first lines of a file, which is the ranged read it became. Each one is weighed by the share of the file its `offset` and `limit` cover, so a hundred lines of a thousand count as a tenth of the file. A denial of a file outside the plugged project (recorded before 0.24.13) is left out of `without` and counted at the foot, and a ranged read of such a file is left out of `instead`: nothing could have delegated it, and nothing of ccsaver's sent the model to it. A ranged read of a file past the byte limit is the exception: the hook never counts its lines ([the event log](#the-event-log) holds `null` there), so the log cannot say what share a range covered, and the report counts the read in `instead` but leaves its tokens out rather than charging the whole file to a hundred lines; so is a PDF read by `pages`, which no line count can weigh; the foot says how many there were. A month where the delegations cost more than the reads they replaced prints a negative saving, in red, with no percentage beside it; a month whose band crosses zero, a loss at the low end of the 1.9–2.8× multiplier and a saving at the high end, says so in words and is painted no colour, because neither would be true.

Six things it cannot see, and says so at the foot when they bite:

- the gate watches the `Read` tool only, so a `Grep` or a `cat` that replaced a denied read is in neither column;
- an endpoint that returns no `usage` block is counted at chars/4, and the report says how many calls that was;
- a month whose denied reads have nothing recorded against them is named as the most flattering reading there is;
- a ranged read of a file past the byte limit, or a PDF read by pages, has no line count to weigh it by, so its tokens are left out of `instead`;
- neither column holds the tokens the session itself read because of ccsaver — [~64 per denial message](measurements.md#what-ccsaver-adds-to-the-sessions-own-context) plus every worker answer it read back — which the foot counts and leaves out of the sum, because the log never says which model was running when an answer came home;
- and neither holds **what a denial costs after the message, which is a request**: when the model, denied, goes back for the file by ranges, each ranged `Read` is one more request, and every request carries the whole conversation again, at the 120,000 tokens of context measured at the median denial fifty to ninety times the message itself ([what a denial costs after the message](measurements.md#what-a-denial-costs-after-the-message)). The hook records the context the session's last request carried beside the model on every line, so the foot counts the denied files that ranged reads followed in the same session, those reads, and the context their requests re-read. A file is one entry per session however many times it was denied there, with every ranged read after its first denial, because `pnpm-lock.yaml` denied again three hours later is the same file let go and asked for again, not a new one; a subagent's lines take no part, denial or read, because the context the hook records is the session's and a subagent's request re-reads its own. The count is wrong in both directions: two ranged reads made in one request re-read the context once, not twice; a `cat`, a `Grep` or a delegation that followed instead is not seen; and each count trails its request by one, since the transcript is written behind the conversation. The other side of that coin is missing too: a denied file the model let go, which is what followed 24 of the 37 denials measured, never sat in the context to be re-read by every later request of the session, and no log counts what did not happen. The calls that came after a denial in the same session are counted beside those reads, because a delegation is what the denial asks for; a `delegate` line holds no path, so which file each one took is not in the log.

The first five lean the same way, towards flattering ccsaver, and the sixth pulls both ways, which is why all six are printed rather than folded in. There is no floor on the sample: the bars are drawn from the first denied read onwards and the three counts over them are what they rest on; a band from two denials is as wide on the page as one from two hundred, and reading it as two is yours to do. A month with no denied read and no ranged read has nothing to set side by side, and says that where the bars would go.
