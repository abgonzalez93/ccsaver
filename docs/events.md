# The event log

What ccsaver records on your machine, and what it never records. Off by default, and no code in ccsaver sends it anywhere.

`ccsaver log on` creates `~/.config/ccsaver/log/` (700), and from then on the hook and the command append one JSON line per event to `events-YYYY-MM.jsonl` (600). The month, in UTC, is the only rotation, and nothing is ever deleted for you. The folder is the switch: without it nothing is recorded and no file is created. `ccsaver log off` renames the folder to `log.off/` with its data, `ccsaver log on` brings it back, and `rm -rf ~/.config/ccsaver/log ~/.config/ccsaver/log.off` deletes it. Either one typed while the log is already so answers `the log is already on` or `off` and touches nothing, the folder included.

It holds metadata only, and it never leaves your machine:

- `gate`: every `Read` the hook sees in a plugged project, allowed or denied. The path relative to the plugged root (a file outside it is `"inside": false`, with no path), `offset` and `limit`, lines (`null` when the file was past the byte limit and its lines were never counted), bytes, the limits and the adapter in force, the model the session was running (`model`, `null` when Claude Code hands the hook no transcript or the transcript names none), the decision and its reason (`under`, `lines`, `tokens`, `range`, `binary`, `unreadable`, `malformed`), the milliseconds since the hook's process started, and the ids Claude Code hands the hook (`session_id`, `tool_use_id`, `agent_id`, `agent_type`, `permission_mode`), which are the ones in the session transcript. A path that is no regular file, a folder or a pipe, is `unreadable` without being opened, so a pipe with no writer at its other end cannot hold the hook.
- `delegate`: one per `bulk-read` or `code-write`. Mode, number of files and how many sat outside the root, characters sent, who answered, why the external worker did not (`outside`, `no worker`, `no key`, `key unreadable`, `key malformed`, `not https`, `status`, `incomplete`, `length`, `timeout`, `not json`, `unreachable`), HTTP status, milliseconds, characters of the answer, the input tokens the external endpoint reported in its `usage` block (`inTokens`, absent when it reported none), the citation tally, the cost of the fallback, the exit code and, for `code-write`, whether there was a target, what the formatter did, the lines written and how many names tripped the `warn:` line.
- `handoff`: `warned`, once per warning, with the token count (`context`), the `limit`, which multiple of it (`tier`) and the `model`; and `written`, with the `lines` and `bytes` of a handoff `ccsaver handoff write` kept, never its text.
- `note` and `fail`: the one-line messages the command prints on stderr, a refusal in an unplugged project included. A mistake on the command line (an unknown command, a command given the wrong arguments, an unknown option, a folder that is not there, a `worker.json` that is malformed or cannot be read, a state folder that cannot be made private) is a `fail`, never a `crash`: `crash` is for a bug in ccsaver, so a machine the user can fix never lands there. `config`: `plug`, `unplug`, `worker set` (host and model), `worker claude` (pinned or not, never the path), `fallback`, `log`, `handoff` (on or off, or the limit), `price` (which model or the worker, and the figure), `launcher` (where it went), and the bare fact of a `key set`; each one only when the value changed, so a setting typed again with the value it already has, which the command answers with `already`, leaves no line. `doctor`: how many `ok`, `warn` and `FAIL` lines. `crash`: name, message and first stack lines of an exception, the ones the hook swallows to let the read through included, and the adapter it could not load (`"where": "hook adapter"`), which is why the `gate` line beside it carries the default limits under the adapter’s name.

To learn the model, the hook reads the **last 64 KB** of the session transcript Claude Code names in `transcript_path` and takes the `model` of the last assistant line in it — parsed as JSON, so a model name written in the conversation is not mistaken for the one in force. Nothing else is read from the transcript and nothing from it is recorded but that one name. It costs nothing while the log is off, because the hook only looks when it is about to write a line. The handoff hook reads the last 256 KB of the same file at the end of every turn, for the token count beside that name, and its `warned` line records those two and nothing else.

Never recorded: the contents of a file, the worker's answer, the text of `--question` or `--spec`, the key, request headers, anything from the transcript but the model name and the token count. A stored key that turns up inside any line, from any command, is written as `[key]`; that holds for keys of 8 characters or more, because replacing anything shorter would eat unrelated text. In an unplugged project the hook records nothing, because it exits before starting Node. A failure to write the log never changes a decision of the hook, an exit code or an output. A failure to *read* it does: a month's file that is there but cannot be read stops `ccsaver saved` with the name of the file, instead of counting as a month with no events, and `doctor` turns it into one `FAIL log:` line and reports everything else as usual.

Every line carries `v` (the format version), `ts`, `kind`, `session` (`CLAUDE_CODE_SESSION_ID`, or `null` outside Claude Code, cut at 200 characters) and `pid`; a line that would pass 4,000 bytes is replaced by a stub with its size, so one runaway message cannot bloat the log. The session id is cut because it is the one field of that stub which comes from outside, and a long one would have carried the stub past the cap it exists to enforce. Processes that write at once do not tear each other's lines: 8 of them appending together left 0 broken lines of 8,000 at 4,000 bytes a line, and 0 of 320 at 1 MB a line (Linux, ext4). While the log is on, the hook also measures the file behind a ranged `Read`, which it otherwise skips. `doctor` leaves one `gate` event per plugged project, marked `"tool_use_id": "doctor"`.
